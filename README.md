# ml-training

> Коротко и по делу — `QUICKSTART.md`. Ниже — подробности по каждой стадии.

Конвейер обучения детекторов «регионов интереса» для мобильного OCR.
Детектор находит область (код контейнера ISO 6346, автономер, что угодно),
текст читают системные движки приложения (Apple Vision / ML Kit) — их
не обучаем. На выходе — `.mlpackage` (iOS) и `.tflite` (Android).

## Три стадии

```
 datasets/<проект>/      1. dataset       2. train        3. export
 размеченные данные ──▶  train/val   ──▶  веса .pt   ──▶  .mlpackage
                         + data.yaml                       .tflite
```

На вход нужен размеченный датасет в YOLO-формате: пары `images/*.jpg` +
`labels/*.txt`. Откуда он взялся — ручная разметка, экспорт из Roboflow,
автоматический сборщик — конвейеру безразлично.

## Быстрый старт

```bash
make install                          # окружение обучения
make install-export                   # окружение экспорта

make projects                         # какие проекты есть
make status P=container-code          # что уже сделано

make dataset P=container-code         # 1) собрать train/val
make train   P=container-code         # 2) обучить
make export  P=container-code         # 3) .mlpackage + .tflite
```

Датасет — это каталог с парами `images/*.jpg` + `labels/*.txt` в
`datasets/<проект>/<любое-имя>/`; `make dataset` подхватывает все такие
каталоги сразу.

## Раскладка репозитория

| Каталог | Роль | В git |
|---|---|---|
| `src/mlkit/` | **ядро**: сборка датасета, обучение, экспорт. О контейнерах не знает | да |
| `projects/<имя>/` | **проект**: `project.yaml` и `samples/` для проверки | да |
| `make/` | по файлу на стадию, все дергают один CLI | да |
| `requirements/` | зависимости по ролям (base / train / export) | да |
| `datasets/<проект>/` | размеченные датасеты (кладутся сюда) | нет |
| `workspace/<проект>/` | всё генерируемое: `dataset/`, `runs/`, `exports/`, `previews/` | нет |
| `weights/` | кэш базовых чекпойнтов (`yolo11n.pt` и т.п.) | нет |

Ядро не содержит ни одной доменной строки: имена классов, гиперпараметры и
имя экспортируемой модели приходят из `project.yaml`. Поэтому новый
детектор — это новый файл конфигурации, а не правка ядра.

## Стадия 1 — датасет (`dataset`)

Объединяет источники, приводит классы, делает детерминированный сплит и
пишет `data.yaml` для ultralytics.

```bash
make dataset-verify P=container-code    # сколько пар нашлось, ничего не пишем
make dataset        P=container-code
make dataset-stats  P=container-code    # боксы, негативные, размеры объектов
```

```bash
make dataset P=… GROUP_BY=roboflow TEST_RATIO=0.15   # разово, без правки конфига
```

Источники по умолчанию — все подкаталоги `datasets/<проект>/`; явный
список — в `dataset.sources`. Правила:

* `workspace/<проект>/dataset/` **полностью пересоздаётся** при каждой сборке —
  правки вносятся в источники, не в собранный датасет;
* **классы**: при одном имени в `classes` вся разметка источников сводится
  в класс `0` (задача «найти регион»), при нескольких — классы сохраняются.
  Подробности ниже;
* **сплит идёт по группам, а не по кадрам** — `dataset.group_by`:
  `stem` (группа = кадр), `roboflow` (копии-аугментации одного снимка),
  `parent` (всё из одного подкаталога), `regex:<шаблон>` (например, код
  контейнера из имени файла). Это единственная защита от утечки: копии
  одного снимка в train и val завышают метрики до бессмысленных;
* деление детерминированное и с соблюдением долей: группы упорядочиваются
  по хэшу имени, доли отрезаются квотами — повторная сборка даёт тот же
  результат, а на маленьком датасете сплиты не остаются пустыми;
* **сплиты «липкие»** (`dataset.stable_splits: true`): при пополнении данных
  уже известные группы остаются в своих сплитах, новые добирают пропорции.
  Без этого каждый добор перетасовывает train и val — метрики соседних
  прогонов становятся несравнимыми, а дообучение с прошлых весов превращается
  в утечку. Раскладка живёт в `workspace/<проект>/splits.json` и переживает
  пересборку датасета; полный пересчёт — `make dataset-reset-splits P=…`;
* `dataset.test_ratio > 0` добавляет отложенный сплит: по нему считаются
  честные метрики (`make test-metrics`), потому что `best.pt` выбирается
  по val и цифра на val всегда оптимистична;
* рядом с датасетом пишутся `manifest.json` (состав источников, счётчики,
  подпись сплита, хэш конфига — копируется в каталог прогона) и `index.csv`
  (кадр в датасете → исходные файлы, чтобы находить, где править разметку);
* кадры без боксов попадают в датасет фоновыми (негативными) — подробности
  ниже.

### Фоновые кадры (без объектов)

Кадры без единого бокса — не мусор: они учат модель не срабатывать на
похожих текстурах. Но доля важна. Ориентир для YOLO — **1–10%** фона
(в COCO их около 1%). Перебор даёт обратный эффект: модель занижает
уверенность и начинает пропускать настоящие объекты.

```yaml
dataset:
  negatives:
    max_share: 0.1     # оставить не больше 10% фоновых кадров
```

```bash
make dataset P=… ARGS="--max-negatives 0.1"    # разово, без правки конфига
```

Как это работает: лишние фоновые кадры отбрасываются **детерминированно**
(по хэшу имени) и **по каждому сплиту отдельно**, поэтому доля соблюдается
и в train, и в val, а повторная сборка даёт тот же результат. Позитивные
кадры не трогаются никогда.

Сборка всегда печатает долю фона, ругается при доле выше 30% и при полном
отсутствии фона; то же проверяет `preflight` перед обучением, а `make
dataset-stats` показывает долю по каждому сплиту. В `manifest.json`
записывается, сколько фона осталось и сколько отброшено.

Отдельная тонкость при авторазметке: пустая метка часто означает не
«объекта нет», а «разметчик не заметил». Такой кадр учит модель худшему —
игнорировать настоящий объект. Поэтому перед тем как поднимать долю фона,
полезно прогнать `make errors`: ложные срабатывания на фоновых кадрах
обычно оказываются пропущенной разметкой.

### Один класс или несколько

Задача «найти регион» одноклассовая: что бы ни было размечено в источнике,
всё сводится в класс `0`. Как только в `classes` появляется второе имя,
режим меняется — классы сохраняются, и появляется вопрос соответствия:
у разных источников своя нумерация.

```yaml
classes:
  - container_code
  - plate

dataset:
  # ключи и значения — номера или имена; имена источника читаются
  # из его data.yaml (Roboflow-экспорт его кладёт)
  class_map:
    code: container_code
    plate: plate
  # своя карта на источник, если нумерация расходится:
  # class_map:
  #   default:    {0: 0}
  #   roboflow-a: {1: 0, 2: 1}
```

Правила простые:

* класс источника, которого нет в `class_map`, в датасет не попадает —
  так отсекается лишнее (`junk`, служебные разметки);
* без `class_map` номера берутся как есть; если встретится номер вне
  диапазона `classes`, сборка **останавливается до записи** и показывает
  файлы-виновники, а не теряет разметку молча;
* `dataset.collapse_classes: auto | true | false` — принудительно свести
  всё в один класс или, наоборот, запретить это;
* сборка печатает боксы по классам и ругается на класс без единого бокса
  и на перекос больше 10:1; то же проверяет `preflight` перед обучением;
* `make errors` при нескольких классах отдельно считает «перепутан класс» —
  это не пропуск и лечится иначе (обычно данными, а не порогом).

## Стадия 2 — обучение (`train`)

```bash
make train-dry P=container-code PROFILE=quality     # что получится, без обучения
make train     P=container-code                     # по конфигу
make train     P=container-code PROFILE=fast        # быстрая проверка идеи
make train     P=container-code EPOCHS=3 DEVICE=cpu # разовые переопределения
make train     P=container-code MODEL=yolo11s.pt    # другая база -> runs/<проект>-yolo11s
make resume    P=container-code                     # после прерывания
```

**Профили** — готовые наборы настроек в секции `profiles`, накладываются
поверх `model`/`train`/`augment`:

| Профиль | Для чего |
|---|---|
| `fast` | 15 эпох, кэш в память — проверить, что данные и пайплайн живые |
| `quality` | imgsz 960, 300 эпох, AdamW, multi-scale, поздний `close_mosaic` |
| `finetune` | дообучение поверх своих весов: замороженный backbone, малый lr |

Свои профили добавляются в `project.yaml` тем же способом. Разовое
изменение любого параметра ultralytics — без правки конфига:

```bash
make train P=… ARGS="--set multi_scale=0.3 --set freeze=10 --set cache=ram"
```

Имена параметров проверяются до старта: опечатка вроде `epohs` больше не
уходит в никуда, а печатается с подсказкой.

**Предполётная проверка** (её же показывает `make train-dry`) ловит то, что
иначе выясняется через часы: пустой или крошечный val, утечку копий между
сплитами, `batch` больше датасета, `close_mosaic ≥ epochs`, `warmup_epochs ≥
epochs`, перекос в сторону негативных кадров, `fraction < 1`.

`device: auto` выбирает cuda → mps → cpu, `workers: auto` — половину ядер,
`batch: auto` — подбор по видеопамяти (только CUDA).

После обучения:

```bash
make runs         P=container-code    # таблица прогонов, лучший сверху
make val          P=container-code    # метрики на val
make test-metrics P=container-code    # честные метрики на отложенном сплите
make errors       P=container-code    # кадры, где модель ошибается
make bench        P=container-code    # мс/кадр, FPS, размер модели
make predict      P=container-code SHOW=1
make tune         P=container-code ITERATIONS=20 EPOCHS=15   # подбор гиперпараметров
```

`make errors` раскладывает худшие кадры в `workspace/<проект>/previews/errors-<сплит>/`
(зелёный — пропущенная разметка, розовый — лишнее срабатывание) и пишет
рядом `problems.csv` — список проблемных кадров с путями к **исходным**
файлам в `datasets/`, чтобы правку разметки не искать вручную. Часто
находится не ошибка модели, а ошибка разметки — это тоже полезно.

Гиперпараметры и аугментации — только в `project.yaml`; флаги CLI нужны для
экспериментов. Прогоны лежат в `workspace/<проект>/runs/<прогон>/` вместе с
`run_info.json` (версии, параметры) и `dataset_manifest.json` (на каких
данных обучено). Ориентир пригодности: mAP50 ≥ 0.85 на **test**.

### Дообучение и повторные прогоны

Когда датасет пополнился, есть три пути.

| Ситуация | Команда |
|---|---|
| Данных стало заметно больше (+30% и выше) | `make train P=… PROFILE=quality NAME=v2` — полное переобучение от базовых весов |
| Небольшое пополнение, хочется быстрее | `make train P=… MODEL=<путь к прошлому best.pt> NAME=v2` — тёплый старт |
| Точечный доменный сдвиг, данных мало | `make finetune P=… FROM=v1 NAME=v2-ft` — профиль `finetune`: замороженный backbone, малый lr, короткий warmup |

Главное правило: **учить всегда на полном датасете**, а не только на новой
порции. Дообучение на одних свежих кадрах приводит к тому, что сеть
смещается к новому распределению и теряет то, что умела.

`make finetune` сам находит `best.pt` нужного прогона и называет новый
`<проект>-ft-<прогон>`; при повторном запуске с тем же именем предупреждает
о перезаписи — задавайте `NAME=`.

Перед стартом сверяется подпись сплита: если она изменилась с того прогона,
чьи веса берутся за основу, выводится предупреждение — часть кадров могла
переехать из train в val, и метрики окажутся завышенными. С включёнными
липкими сплитами такого не происходит.

Сравнивать прогоны:

```bash
make runs         P=…            # таблица: mAP50, mAP50-95, эпохи, база
make test-metrics P=… RUN=v2     # честная цифра на отложенном сплите
make errors       P=… RUN=v2     # что именно стало лучше или хуже
```

## Стадия 3 — экспорт (`export`)

```bash
make export P=container-code                  # веса runs/<проект>/weights/best.pt
make export P=container-code RUN=container-code-yolo11s
make export-pretrained MODEL=yolo11n.pt       # готовая COCO-модель
```

Результат: `workspace/<проект>/exports/ios/<model_name>.mlpackage` и
`.../android/<model_name>.tflite`. Форматы задаются `export.formats`
(`coreml`, `tflite`, `onnx`, `torchscript`).

**Перед переносом в приложение — сверка:**

```bash
make export-check P=container-code    # те же кадры через .pt и через экспорт
make bench-export P=container-code    # скорость мобильных форматов
```

Экспорт ломается тихо (нормализация входа, порядок выходов, потерянный
NMS), а метрики после него никто не пересчитывает. `export-check` прогоняет
одни и те же картинки через исходные веса и через экспорт и сравнивает
боксы по IoU; расхождения на уверенных боксах — ошибка, пограничные
(разное подавление дубликатов) — предупреждение. CoreML читается в `.venv`,
TFLite — в `.venv-export`, цель `export-check` запускает оба.

* CoreML по умолчанию **без встроенного NMS** — постобработку делает
  приложение; `export.coreml_nms: true` вернёт готовые боксы Apple Vision.
* `export.tflite_int8: true` — int8-квантизация (нужен собранный датасет
  для калибровки).
* Архитектура (классическая v8/11/12 или end-to-end v10/26) определяется по
  самим весам, так что экспорт корректен и для прогонов с `MODEL=`.

Экспорт идёт в отдельном окружении `.venv-export` — `make export` следит
за этим сам, `make pipeline` перезапускает в нём только стадию экспорта.

mkdir -p projects/seal-number/samples

## Окружения

| Окружение | Ставится | Для чего |
|---|---|---|
| `.venv` | `make install` | сборка датасета и обучение |
| `.venv-export` | `make install-export` | экспорт моделей |

Python 3.10–3.13 (**не 3.14+**: под него нет колёс tensorflow), в Makefile
закреплён 3.12; используется `uv`, при его отсутствии — `python3.12 -m venv`.
Окружения не смешивать: в обучающем `.venv` TFLite-экспорт ломает связку
torch/torchvision, а coremltools 9 несовместим с numpy 2.5.

```bash
make doctor P=container-code     # python, torch, mps, .venv-export, источники данных
```

## Частые сценарии

| Задача | Команды |
|---|---|
| Есть готовый датасет | положить в `datasets/<проект>/`, затем `make pipeline P=…` |
| Пришли новые данные | `make dataset P=… && make train P=…` |
| Полный цикл одной командой | `make pipeline P=…` |
| Проверить настройки перед долгим обучением | `make train-dry P=… PROFILE=quality` |
| Выжать максимум качества | `make train P=… PROFILE=quality`, затем `make errors P=…` |
| Дообучить на пополнении | `make train P=… PROFILE=finetune MODEL=workspace/<проект>/runs/<прогон>/weights/best.pt` |
| Понять, каких данных не хватает | `make errors P=… LIMIT=30` |
| Сравнить прогоны | `make runs P=…` |
| Убедиться, что экспорт не сломан | `make export-check P=…` |
| Проверить, как VLM видит одно фото | `make preview P=… IMAGE=<файл> SHOW=1` |
| Сравнить n и s | `make train P=…` и `make train P=… MODEL=yolo11s.pt`, сравнить mAP |
| Быстрая проверка пайплайна | `make train P=… EPOCHS=3` |
| Посмотреть модель глазами | картинки в `projects/<проект>/samples/`, затем `make predict P=…` |
| Начать задачу заново | `make clean P=…` (датасет и прогоны) или `make clean-all P=…` (всё) |

Шпаргалка по всем командам и типичным сценариям — `docs/cheatsheet.md`.
Полный список: `make help`; флаги любой стадии: `make cli ARGS="train --help"`.
Прямой запуск без make: `bin/mlkit status container-code`.
